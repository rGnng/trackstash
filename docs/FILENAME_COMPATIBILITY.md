# 文件名兼容性要求（NTFS / exFAT / APFS）

| | |
|---|---|
| **状态** | 规则已确定，已实现并测试 |
| **要求** | 文件名需要最大兼容 NTFS 和 exFAT，避免跨文件系统复制出错 |
| **依据** | NTFS/exFAT 的公开限制 + 对现有 20,829 首曲目的只读审计 |

## 1. 目标文件系统的限制

| 项目 | NTFS | exFAT | 本项目规则 |
|---|---|---|---|
| 单个名字长度 | 255 UTF-16 码元 | 255 UTF-16 码元 | 每个组件 ≤ 253 码元（扩展名计入，留余量） |
| 禁止字符 | `\ / : * ? " < > |` 和 `0x00–0x1F` | 同上（macOS 上能创建，但 Windows 读不了） | 全部替换为 `_` |
| 末尾空格或点 | 不允许 | 不允许 | 目录末尾 `.` → `_`；空白删除；文件标题末尾的 `.` 在扩展名前保留（`x..m4a`，以扩展名结尾） |
| 保留名 | `CON PRN AUX NUL COM1–9 LPT1–9` | 同上 | 主名（第一个 `.` 之前）命中则最后一个字符换成 `_`，统一大写。`CON.txt` → `CO_.txt`，`COM10` 不是保留名 |
| 大小写 | 不区分 | 不区分 | 同一目录内大小写重名按冲突处理（见第 4 节） |
| 路径总长 | 旧版 MAX_PATH 260；启用长路径后无此限制 | 无 | 审计最长相对路径 174 码元，加上盘符仍在 260 内 |

## 2. 现有库的审计结果（只读）

对 `itunes_export.tsv` 的 20,829 首逐一检查：

| 检查项 | 结果 |
|---|---|
| 组件超过 255 码元 | 0 |
| 含禁止字符 | 2（见第 3 节） |
| 末尾空格或点 | 0 |
| 保留名（含扩展名） | 0 |
| 同目录大小写重名 | 0 |
| 最长相对路径 | 174 码元 |

## 3. 需要处理的两首

- `…/8_13.ワンダーラスト *200221 remix.m4a`
- `…/16_22.まったりお茶でもいかが? feat.初音ミク.m4a`

这两首是源文件名（iTunes 没有整理），文件名里有 `*` 和 `?`，NTFS 不允许。TrackStash 整理时会把它们替换为 `_`。

## 4. 大小写与 Unicode

- **大小写冲突**：NTFS 和 exFAT 都不区分大小写，`Track.m4a` 和 `track.m4a` 是同一个文件。导入和整理时用 `exists()` 检测，冲突时加 ` (2)` 后缀（已有逻辑）。
- **已存在的目录不改大小写（与 Music 一致）**：目标目录已经存在、只差大小写时，TrackStash 不重命名它，文件直接放进这个目录。
- **数据库记录磁盘上的真实拼写**：导入、整理、整库搬迁写入数据库前，都会按目录项解析出真实的大小写和 Unicode 形式（`resolve_disk_path`）。这样数据库里的路径与文件系统一致，搬迁到大小写敏感的系统后也能找到文件。整理时如果发现"目标已存在且是同一个文件"，只更新数据库路径，不移动文件。
- **Unicode 形式**：TrackStash 为自己入库和整理的文件生成的名字都是 NFC。普通复制（`cp`、Finder 等）会原样保留源端的名字字节，跨盘后的形式由复制工具和文件系统决定，不在 TrackStash 的范围内。
- 音乐盘上现有约 3,036 个 NFD 名字，是 macOS 写入时的存储形式。只有 TrackStash 重新整理这些文件时，名字才会按规则变成 NFC。

## 5. 与 Music 行为的差异

- 保留名：Music 的规则与本项目一致（`CON`/`con` → `CO_`），但 Music 不处理 `CON.txt`，本项目按 NTFS 的规则处理，会和 Music 不同。这是有意的差异，以兼容性为准。
- 其他规则（禁止字符、末尾空白、前导空白、长度、扩展名大小写）与 Music 保持一致。
